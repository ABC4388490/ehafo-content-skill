# 易哈佛内容自动化

把任务视为一次完整生产运行，不只写初稿。默认使用简体中文。

## 核心原则

1. 选题只由用户价值决定，品牌转化不得参与选题、评分或排序。
2. 易哈佛问题中心 `https://www.ehafo.com/exam/questions/` 是用户问题型 QA 的主要选题库，不是年度政策的最终事实来源。
3. 所有时效性、政策性和地区性事实必须回到适用年度的官方一手来源。
4. 发现可修复的问题时直接修订并复检，不得停在问题清单、改进建议或要求用户再次确认。
5. 不把“字段齐全”当成“内容有用”。按四级状态输出：
   - `DRAFT_PASS`：事实和格式合格，但独立用户测试仍发现未解决问题，只能继续改稿；
   - `VALUE_UNPROVEN`：独立用户测试通过，但没有真实发布数据证明效果，只能称为待验证成品；
   - `AUTO_RELEASE`：事实、用户任务和同类历史表现均达到预先声明的标准；
   - `BLOCKED`：关键事实缺失、来源冲突或用户核心任务无法完成。
6. 不以免责声明弥补事实缺失，不用“以官方为准”掩盖未经核验的具体信息。
7. Skill 负责生成和验证；除非已有获授权的发布工具且用户明确要求发布，否则不得声称已发布到微信。
8. 默认自主完成“选题—形式—生产—验证—修订”全流程。除非用户明确只要分析或方案，否则不得停在推荐选题、形式判断、问题诊断或要求用户补写下一条指令。
9. 文章价值必须在开头立即兑现，并在手机端保持可读。不得用信息完整掩盖重点后置、文字拥挤、视觉层级缺失或图文重复。每篇服务号文章必须包含 1—2 张承担解释任务的正文插图，不得为 0 张或超过 2 张；固定顶部图、固定底部图和 Logo 不计入数量。
10. 文章必须包含 1—2 张正文插图；已有插图只有在与当前事实、任务和视觉规则完全匹配时才可复用。需要新生成或修改正文插图、贴图时，必须同时使用 `remotion-best-practices` Skill，通过 Remotion React 组件制作并用 `npx remotion still` 渲染静态图片。本 Skill 负责事实、内容任务、品牌和发布门禁。固定品牌首尾图属于原始资产，只能原样复用，不得通过 Remotion 重绘。
11. 把发布视为反馈闭环的起点，不是任务终点。真实数据可用时，将用户问题、内容表现、事实错误和返工原因沉淀回选题库、知识库、模板或门禁；不得只看数据而不更新规则，也不得根据单篇短期波动频繁改方向。
12. 把真实任务和用户确认过的改进作为本 Skill 的持续学习来源。每次运行结束检查是否出现可复用规则；达到下述门槛时直接更新本 Skill、完成校验并保存，不再等待用户重复提出“写入 Skill”。
13. 每篇服务号文章同时生成文章标题、摘要和 `article_cover` 封面。三者必须连续分工：封面给行动、风险或结果，标题提出真实问题，摘要提前回答并说明适用边界；不得逐字重复同一句话。

## 自动沉淀规则

满足以下任一条件，且能直接改善易哈佛内容选题、核验、生产、排版、发布或复盘时，自动写入：

- 同类问题重复出现，并已确认产生它的共同流程或规则；
- 某项规则缺失导致可观察的成品失败，修正后已经实际验收通过；
- 用户明确确认一项长期适用的品牌、内容、图片或工作流程要求；
- 真实发布数据在完整观察窗口和足够样本中呈现稳定规律。

写入前先搜索现有 Skill，避免重复；与旧规则冲突时修改原规则，不并列保留矛盾版本。核心流程写入 `SKILL.md`，形式细节写入对应 `references/`，确定性检查优先写入现有脚本。更新后使用 `skill-creator` 完成校验和保存，并向用户简要说明写入了什么。

不得自动写入：

- 只适用于当前一篇内容或一个页面的一次性要求；
- 尚未验证的猜测、单篇短期数据或偶然表现；
- 纯理论、背景知识或不能转化为执行动作的读书笔记；
- 已被现有规则完整覆盖的同义内容。

## 默认自主运行

用户只要表达“开始生产”“生成今天的内容”“继续做内容”或同等意图，即进入自主运行：

1. 根据当前日期，跨护士、护师、医师、药师等现有内容范围寻找真实候选题；
2. 结合问题中心、已有知识库、官方考试节点和近期已做内容，选择当前用户价值最高且不重复的一个选题；
3. 自主判断采用标准内容或 QA 结构，并选择考讯、文章、贴图或必要组合；
4. 直接完成官方核验、成品生成和自动验证，不要求用户先决定题目、考试类型、内容结构、发布形式或张数；
5. 只有出现彼此冲突且无法从已有规则消解的业务范围，或完成成品必须依赖用户尚未提供的私有素材/权限时，才询问一个最关键问题。

不得把“你可以这样下指令”作为默认交付，也不得在完成形式判断后等待用户再次确认。

## 输入解析

从用户请求中识别：

- 内容范围：考试、年份、地区、用户阶段；用户未指定时，从当前可覆盖的考试范围中自主选择，不因此追问；
- 形式偏好：考讯、文章、贴图方案、完整图片或整套内容；同时识别用户指定的是“用户问题型 QA”（报名、审核、考试、成绩、证书、备考方法等真实疑问）还是“题目解析型 QA”（每日一题、一题一解、病例题）。QA 是内容结构，不是独立发布载体，仍须选择文章、单张贴图或多张贴图承载；用户未指定时自动决定，用户指定时仍先检查适配性；
- 数量：未指定时只生成一个最高价值选题，并完整生产为成品；
- 时点：使用当前日期判断内容是否仍有行动价值；
- 素材：问题页、知识库、官方通知、原始 Logo。

信息不足时不要先追问。先在问题中心、用户知识库和官方来源中补齐；考试、地区或目标形式未指定时均由系统比较后决定。只有存在无法消解的互斥业务约束，或缺少不可替代的私有素材/权限时，才询问一个最关键问题。

## 图片生产四道硬门禁

任何新建或修改图片的任务都必须依次通过以下四道门禁。门禁未记录、未验证或任一项失败时，立即停止交付并进入 `BLOCKED`；不得用目视感觉、口头声明或后续补检代替。

1. **先声明类型**：生成或修改前，必须在验证包的 `production_gates` 中把 `asset_type` 和 `template_type` 明确声明为 `article_cover`（文章封面）、`article_illustration`（文章正文插图）或 `service_account_cards`（服务号贴图），两者必须相同。一次生产包含多类图片时，`production_gates` 使用数组逐类登记，不得把封面与正文插图挤进同一条记录。类型未声明前不得选择画布、模板、Logo、信息密度或导入方式；禁止混用三类模板。
2. **锁定固定资产**：原始 Logo、固定顶部图、固定底部图和固定品牌尾图默认全部不可编辑，只能原样插入。任务开始前记录其 SHA-256，结束后再次核对；调整正文信息图或其他图片不得波及这些资产。只有用户明确把某个固定资产作为独立修改目标，并完成该资产规则要求的确认流程时，才可解除对应锁定。
3. **限定修改白名单**：修改任务开始前，先用 `scripts/verify_edit_scope.py snapshot` 保存项目文件指纹；再把用户明确要求修改的组件或文件逐项列入 `--allow`。完成后使用 `verify` 检查：新增、删除或修改任何白名单外文件均失败；所有锁定资产必须通过 `--lock` 复核。用户只要求改正文信息图时，白名单只能包含该正文信息图组件及其直接生成物，不得顺带修改 HTML、其他图片组件、固定资产或共享模板。
4. **多维验收**：交付前必须同时把内容准确、实际可读尺寸、图片比例、资产完整性和对应发布场景的手机端效果记录为 `pass`。文章封面检查横版与方版缩略图，正文插图检查约 390px 正文，服务号贴图检查实际发布尺寸。五项中任何一项缺失或不合格都不得交付；脚本通过不能替代手机端目视验收，目视正常也不能替代事实、比例、指纹和修改范围检查。

## 生产流程

### 1. 建立候选选题

优先读取用户指定素材。默认入口：

- 易哈佛医学考试问题中心：`https://www.ehafo.com/exam/questions/`
- 用户现有的考试知识库与品牌规范。

将问题中心作为用户问题型 QA 的主要内容范围：优先从现有页面的问题标题、所属考试、用户阶段和相关问题中选择主题，不直接复制页面原文。竞品内容只用于学习选题表达、标题和组织方式，不得替代易哈佛问题中心确定 QA 内容范围，也不得替代官方事实来源。

用户未指定具体选题时，读取 [topic-value-gate.md](references/topic-value-gate.md)，建立彼此实质不同的真实候选题并完成自动选题。候选数量由当前确有证据的用户问题决定，不得用近义题凑数，也不得先认定一个题目再补评分证明它最好。

先执行价值硬门槛，再严格按 `topic-value-gate.md` 的 0–5 分锚点评分。评分只衡量用户即时收益、覆盖人数、避免损失、可执行性和当前相关性。每项必须写出观察事实、对应档位和依据类型；证据不足时取低分，不得为了达到 65 分倒推分数。任一项为 0 分时不得自动选择。

若当前存在已核验的重大官方事件或临近截止事项，执行时效优先规则；否则选择综合分最高者。分数相同时依次比较：避免损失、即时可执行性、覆盖人数。

用户已指定具体选题时不进行候选排名，但仍执行价值硬门槛。选题不能明确服务对象、现实问题和具体行动时，拒绝生成并说明该题为何没有达到内容价值门槛。

### 2. 建立用户任务卡

读取 [user-task-gate.md](references/user-task-gate.md)，先形成用户任务卡，再核验和生产。至少明确：

- 用户此刻处于什么状态；
- 他真正要完成的决定或动作；
- 看完后能得到什么可验证结果；
- 哪些问题必须在成品内回答；
- 是否仍需另找一篇攻略才能完成任务。

若核心任务无法被当前官方信息完整支持，进入 `BLOCKED`；不要生成泛泛科普。

### 3. 核验事实

读取 [source-gate.md](references/source-gate.md) 并建立事实卡。

必须浏览或读取当前可用来源，不依赖模型记忆回答可变信息。对报名日期、报考条件、工作年限、费用、审核、准考证、考试安排、成绩、证书和地区政策逐条核验。

官方来源的适用考试、年份、地区和事项必须与正文完全一致。来源冲突、来源缺失或适用范围不明时进入 `BLOCKED`。

### 4. 选择成品形式

先读取 [format-gate.md](references/format-gate.md)，完成形式决策；确定形式后再读取 [output-templates.md](references/output-templates.md)。选择文章时还必须读取 [article-mobile-layout.md](references/article-mobile-layout.md)。

- 考讯：回答“现在发生了什么、影响谁、现在做什么”。
- 文章：回答“我这种情况怎么办”，按情形拆解。
- 贴图：用于快速判断、收藏和转发；不是把文章机械分段。
- QA：分为“用户问题解答型”和“题目解析型”。前者围绕问题中心中的真实疑问交付结论、情形判断和行动步骤；后者围绕一道考试题完成作答、解析和同类练习承接。用户要求 QA、问答、每日一题、一题一解或病例问答时，读取 [qa-content-patterns.md](references/qa-content-patterns.md)，再选择文章或贴图作为载体；不得把 QA 当成第四种发布形式。
- 只选择能增加独立用户价值的形式。不得把“用户要求一套或全部”直接解释为三种形式全部生成。
- 允许单一形式，也允许必要组合；组合中的每种形式必须承担不同任务。
- 用户指定的形式不适合选题时，不强行生成。输出形式判断和替代形式，再交付适合的成品。
- 多张贴图必须有至少 3 个互不重复、适合快速扫读的信息模块；不满足时不得拆成多张。
- 基于同一事实卡生成所有已选形式，禁止事实漂移。
- 选择文章时，标题、摘要和文章封面属于文章的必要发布字段，不作为额外内容形式计数；使用同一事实卡生成并执行“承诺—答案—行动”检查。

成品生成后必须按 [user-task-gate.md](references/user-task-gate.md) 执行独立用户测试，并完成“承诺—答案—行动”检查：

1. 首图、副标题和摘要承诺解决的每个核心问题，必须能定位到后续具体模块；
2. 按用户真实决策或办理顺序组织内容，不按法规条款或资料来源顺序堆放；
3. 每个模块必须回答一个具体问题，同时给出明确结论和下一步动作；
4. 删除对当前用户无新增价值的报考前置常识、法规摘录和重复定义；
5. 不得用“自行查询”“自己去问”“以当地为准”代替答案；存在地区差异时，仍须给出全国通用结论、具体官方查询入口名称和需要核对的事项。
6. 文章开头必须在前 3—5 个短段内直接回答最吸引点击的核心问题，给出最重要的行动或风险，并说明下文能解决什么；不得先写行业背景、创作缘由、来源介绍或“最近有人写错了”。
7. 文章必须通过约 390px 宽度的手机端阅读检查：普通内容主动变轻，关键结论有停顿，一屏原则上只承担一个核心意思；不得把连续说明书式段落仅靠小标题分组后视为排版合格。
8. 文章插图不得重复正文整段文字。逐张写明它提供的独立信息；删除后不损失对象识别、关系理解、操作确认或必要情境的图片，视为装饰图并直接从文章中删除。不得为了图文节奏预设插图张数。

任一首图承诺未兑现，或用户看完仍不知道下一步做什么，不得进入 `VALUE_UNPROVEN` 或 `AUTO_RELEASE`。能修订则标记 `DRAFT_PASS` 并继续改稿；受官方信息缺失限制则进入 `BLOCKED`。

再读取 [quality-revision-gate.md](references/quality-revision-gate.md)，执行同类内容对比和自主修订。公开同类内容存在时，成品不得只改标题后重复其信息清单；必须用可靠事实新增一个用户决策、异常处理、执行路径或更清晰的高风险提醒。不得为了显得不同而加入无关信息、未经核验经验或冗长解释。

把 `DRAFT_PASS` 视为内部迭代状态：只要问题可通过改稿解决，就直接修订并重新执行事实核验、用户任务测试和质量复检，不向用户停在“发现问题”阶段。连续三轮仍无法解决时，才输出 `DRAFT_PASS`；若原因是官方信息不足，则输出 `BLOCKED`。

### 5. 应用品牌规范

读取 [brand-rules.md](references/brand-rules.md)。

先完整提供内容价值。只有易哈佛产品确实能帮助用户完成下一步时，才可在正文结束后加入一个自然 CTA；不匹配时不加 CTA。CTA 必须与用户当前考试阶段及刚完成的任务直接相关：报名阶段可承接报名后的备考行动，准考证阶段可承接考前练习，成绩或证书阶段不得强行引导刷题；没有阶段匹配的产品动作时不加 CTA。品牌或产品承接不得反向改变选题和事实结论。禁止制造焦虑、虚假权威和通过承诺。

需要制作新文章封面、正文信息图或贴图时，同时加载并遵守 `remotion-best-practices` Skill；使用 Remotion React 组件制作并渲染静态图片，不得绕过本 Skill 的事实核验和品牌门禁。

先判定图片用途，再应用对应规则。文章列表、分享和缩略入口使用的图片一律按“文章封面”处理；发布在服务号文章正文中、随正文滚动阅读的图片一律按“文章正文插图”处理；作为独立图片消息或成组图片供用户脱离文章阅读、收藏和转发的内容一律按“服务号贴图”处理。三者是不同成品，禁止共用画布、Logo、信息密度、导入方式或验收门槛。

文章正文插图与服务号贴图共同底线：

1. 默认使用纯白或单一浅色画布，不生成背景图；
2. 禁止渐变、纹理、照片、人物、场景、插画、装饰图案等背景元素；
3. 不得靠放大标题、重复文字或增加装饰填满画面；
4. 图片内的政策、时间、条件和行动建议必须与事实卡一致。

文章标题、摘要与封面规则：

1. 先确定三者分工：封面让目标用户立即识别行动、风险或结果；文章标题明确提出正文真正回答的问题；摘要提前交付核心结论、适用边界和阅读收益。不得把同一句话复制三遍；
2. 封面主文案控制在 6—14 个汉字、2—3 行，每行约 3—7 个字。一张封面只表达一个意思，默认优先行动型，其次问题型或克制的风险型；保留完整语义单元，不拆开数字与量词；
3. 封面承诺必须由正文兑现。正文没有步骤时不得写“按这几步”，没有明确清单时不得写具体数字；禁用“一文看懂”“重磅”“速看”“建议收藏”“真相来了”“不看后悔”等空泛或诱导词；
4. 文章标题优先使用 12—26 个汉字，并保持在平台 64 字上限内。标题标明对象或情境，提出正文能直接回答的核心问题；不使用绝对化结论、未经证明的变化、夸张数字或焦虑表达；
5. 摘要不得留空或依赖平台抓取正文开头。控制在 45—75 个汉字且不超过 120 字；第一句直接给核心结论，随后说明地区、年份、对象或条件边界，最后交代读完能完成什么；不写“本文将介绍”“下面一起来看看”；
6. 文章封面声明 `article_cover`。使用 [PosterCoverTemplate.tsx](assets/PosterCoverTemplate.tsx) 或项目已有同类 Remotion 组件分别渲染 `900×383` 横版和 `500×500` 方版 PNG；两版使用相同文字、颜色和字体，但独立调整换行、字号和位置，不从一张图片自动裁切另一张；
7. 封面只使用纯色背景和文字，不使用照片、渐变、纹理、插画、图标、阴影、描边或装饰线。只能从 3 套固定色板中选择：`action_green` 用于办事、材料核对、方法和长期内容；`notice_blue` 用于政策通知、时间安排和结果发布；`risk_red` 只用于截止、资格不符、遗漏或其他高损失风险。先判断风险，再判断通知，其余统一用绿色；不得按护士、医师、药师等考试品类分色，不得为了新鲜感轮换或新增色板。三套均使用米白主字和黄色单点强调，最多强调一个字符、数字或短词；
8. 所有封面文字与背景的对比度不得低于 `4.5:1`。分别缩到约 `235×100` 和 `100×100` 检查主文案仍能一眼读完，并检查无溢出、错误断词、边缘贴字或两版语义漂移；
9. 原始 Logo 存在时只允许等比例缩放和移动，不得重绘、改色或变形；没有独立原始 Logo 文件时输出无 Logo 封面，不得从固定首尾图裁取；
10. 在 `outputs.article.cover` 中登记封面文案、文章标题、摘要、双尺寸路径和像素尺寸、`palette_id`、固定纯色配色及 `thumbnail_readability: pass`。验证脚本必须拒绝未知色板或被修改的色值；事实、尺寸、可读性、比例、资产完整性和移动端效果任一未通过时不得交付。

服务号贴图规则：

1. 把每张贴图视为可脱离文章独立阅读和传播的内容成品，不把文章段落机械切成图片；
2. 每张只承担一个明确的信息任务，同时给出结论、必要细节和下一步动作；多张贴图保持统一比例、边距、字号层级和视觉节奏；
3. 首图同时承担点击封面和实用信息任务，用用户关心的结果、风险、遗漏或行动作标题钩子，明确看完能获得什么；不得使用“材料关系”“内容总览”等说明书式标题，也不得制作只有标题的空封面；
4. 使用用户提供的原始 Logo 文件程序化叠加到左上角，只允许等比例缩放和移动，不得 AI 重绘、变色、变形或调整内部间距；没有原始 Logo 文件时，只交付无 Logo 底图并标记 `ASSET_BLOCKED`；
5. 留白用于建立层级和扫读节奏，可以比文章插图更充足；不得直接套用正文信息图的 `72%` 内容占比、`15%` 上下空白、`900×480/540/600` 画布或约 390px 正文显示门槛；
6. 按整套贴图的实际发布尺寸进行手机端预览，检查单张是否完整、系列是否统一、文字是否清楚、每张是否具有独立价值；不得仅凭像素占比判断贴图合格；
7. 全部内容图之后追加固定品牌尾图 [ehafo-brand-promo.png](assets/ehafo-brand-promo.png)。尾图是独立品牌宣传页，不计入内容图数量，不替代任何内容图；
8. 直接复制固定品牌尾图原文件，不得通过 Remotion 重绘、裁剪、改字、覆盖文字、调整版式、变色、加滤镜或重新压缩；交付前核对 SHA-256 为 `56f998e0802d34b23077036160f380e4fd14bda1fbf5e192fae8222f69f1343c`。

文章正文插图规则：

1. 每篇服务号文章强制使用 1—2 张正文插图；不得交付 0 张插图的纯文字文章，也不得超过 2 张。固定顶部图、固定底部图、Logo、二维码和品牌宣传图均不计入正文插图数量，不能用于满足此门禁；
2. 把插图视为正文的解释工具，只用于呈现文字难以快速说明的关系、步骤、对照、时间节奏、判断路径或操作确认。生成前逐张写明一条图片独有信息；删除后不影响理解或行动的图片视为装饰图，必须换成真正承担解释任务的插图，不得以删除后变成 0 张作为交付结果；
3. 把正文内容转成信息图后，删除正文中与图片同义的清单、步骤或事实复述；正文只保留来源、适用边界、风险解释、无障碍替代信息或图片未承载的补充行动；
4. 服务号文章固定顶部图 [ehafo-article-header.png](assets/ehafo-article-header.png) 原样放在预览中的“标题＋摘要”之后、正文首段之前；正式写入微信时，标题与摘要使用微信独立字段，顶部图因此仍是正文第一项。顶部图必须是窄版纯白品牌页眉，只保留原始 Logo、细分隔线和连续口号，不得出现灰色页面底、截图残留、外层圆角卡片、描边、投影或大块上下空白。正文结束后原样使用固定底部图 [ehafo-article-footer.png](assets/ehafo-article-footer.png)。两图不计入正文信息图数量；
5. 固定首尾图不得通过 Remotion 重绘、裁剪、改字、覆盖文字、调整版式、变色、加滤镜或重新压缩，只能在文章中按原比例显示。交付前分别核对 SHA-256：顶部图 `23081faf27778eb9372fccfe4ae82e7a7b48f748a0e5a3327e2c5de02b4a64c9`，底部图 `e7ba40c3e1742c10958a91a764a8ab42a9eaab2352cd1f87cb260399cd4ec84d`；
6. 文章已使用固定顶部图时，Remotion 正文信息图禁止再次放 Logo；
7. 正文信息图使用内容驱动的画布高度，不把服务号贴图的竖版长图、多张卡片纵向堆叠或独立传播样式搬进文章。默认保持 900px 宽，优先使用横向流程、两列对照、2×2 关系或其他紧凑结构；先完成内容排版，再以最下面一行可见文字或确有信息作用的图形底边为裁切基准。最后一行内容下方只保留 24—36px 的呼吸边距，随后立即结束图片。文字已经结束但背景仍继续向下延伸，或为了上下“视觉均衡”保留一整块空画布，均直接判定不合格；
8. 正文信息图必须通过 `scripts/check_image_density.py`：有效内容纵向占画布高度不少于 72%，顶部空白不超过 15%，最后一个有效内容元素以下的底部空白不超过 8% 且不得超过 48px。任一条件不通过时，优先直接缩短画布，其次压缩模块间距或改为横向紧凑结构；不得通过向下移动内容掩盖底部留白；
9. 信息较少时使用“标题＋一个核心关系＋一条行动核对”的紧凑结构；标题、主体模块、结论之间采用连续阅读节奏，不把模块平均分散到整张画布。最后一条结论或说明文字就是图片的视觉收口，不在其下继续保留空模块或均衡留白。仍撑不起画面时直接缩短图片高度，或改成更短的信息卡、把结论放回正文；禁止放大字号、拉大模块间距或增加无价值装饰来填满画面。缩放到约 390px 文章宽度后，正文级图片文字不得小于约 15px；
10. 正文信息图最外层禁止使用描边、圆角卡片外壳、阴影、灰色页面底或“白底里再悬一张卡片”的框架。默认让图片画布使用与服务号正文一致的纯白背景，主体直接落在画布安全区内；内部用于区分步骤、条件或选项的局部浅色卡片可以保留，但不得连成包围整张图片的外框；
11. 把正文信息图插入 HTML、公众号预览或微信正文时，图片容器不得再次添加边框、圆角、阴影、底色或额外卡片式内边距。仅保留完成阅读节奏所需的上下间距，并以约 390px 手机端实际效果验收图片是否自然融入正文。
12. 渲染后必须打开成品目视检查“最后一行文字—图片底边”这一段：若肉眼可见的空白明显大于一行正文高度，或使图片在文章中呈现“内容已经结束、画布仍未结束”的感觉，即使脚本因浅色元素误判为通过，也必须重新裁切后再验收。此规则只用于文章正文插图，不用于服务号独立贴图或固定品牌首尾图。
13. 正文插图必须按原始宽高比完整缩放进正文，不得使用裁切填充。图片及其外层容器禁止固定像素宽度、`min-width`、横向位移、`overflow: hidden`、`object-fit: cover` 或其他会在手机端隐藏左右内容的样式；使用微信兼容的等效行内样式实现 `width:100%; max-width:100%; height:auto; display:block; margin-left:auto; margin-right:auto;`。
14. 正式写入微信时优先通过公众号编辑器“上传图片”插入，不得从第三方排版工具或网页直接复制带有固定宽度和裁切容器的整个图片模块。若必须经过第三方工具，写入后仍须检查并清除图片和外层容器的固定宽度、负边距、变换位移与溢出隐藏。
15. 文章正文插图左右各保留不少于画布宽度 6% 的内容安全区，标题、数字、步骤序号、结论和操作按钮不得进入安全区；该安全区用于提高正文缩放和编辑器兼容性，不代表允许公众号裁切图片。
16. 文章插图的通过标准是：在约 390px 的微信正文内、不点击图片放大即可看到完整四边、全部标题和关键信息，页面无横向滚动。若点击放大后才完整，直接判定为横向裁切失败，先修复导入样式或图片结构再交付。不得用“点击可查看完整图”作为解决方案。
17. 不因文章插图出现横向裁切，就把服务号贴图统一改为 `1080×1440`、`1080×1350` 或其他竖版比例。文章插图继续采用默认 900px 宽、内容驱动高度；只有在约 390px 正文宽度下文字无法读清或关系无法辨认时，才拆图、缩短横向结构或改用更适合正文的比例。此条不改变服务号贴图的独立发布尺寸与整套验收规则。
18. 不把图片文件的像素宽度等同于正文中的视觉大小。顶部图、正文信息图和底部图都必须检查“有效内容宽度”：排除纯背景后，主要内容在典型有效行上的横向跨度原则上不少于整张画布的 75%；正文信息图的核心卡片或关系图优先占 82%—92%。左右安全区包含在剩余空间内，不得出现“整图铺满正文、真正内容只缩在中间”的双重留白。
19. 按约 390px 正文宽度换算最终字号，使用 `最终显示字号 ≈ 图片内字号 × 390 ÷ 图片像素宽度`。正文信息图的普通说明文字不得小于约 15px，标题和关键结论应明显高于正文；固定首尾图中的主要文字也必须在不放大图片时可读。若字号不足，优先放大内容、收窄内部画布或重新排版，不得只提高导出分辨率。
20. 固定顶部图和固定底部图属于锁定资产。任何文章生产、正文插图优化、导入排版或手机端适配任务都不得顺带修改、重排、裁切、重绘、压缩、替换或制作候选版本；尤其不得以“实显偏小”“版式统一”或“通过门禁”为由改动固定底部图。若实显检查发现问题，只报告问题并保持原文件不变。只有用户明确单独要求修改某一固定图时，才进入该资产的独立修改任务；修改前先说明方案，得到确认后再制作，并在再次确认后更新资产及 SHA-256。
21. 正文插图必须通过“文章阅读节奏门禁”。默认让单张图片在约 390px 正文宽度下的显示高度不超过其显示宽度，且不连续纵向堆叠超过 3 个同构卡片。若图片需要四层以上纵向卡片、接近或超过一整屏才能读完，或视觉上像一张缩小后的服务号贴图，直接判定过长：优先改成横向流程、两列或 2×2 结构；仍无法紧凑表达时拆成两张各自有独立任务的插图，或把次要信息放回正文。不得仅通过压缩字号、减小行距或缩小内容来满足高度限制。
22. 文章正文插图不得追求“脱离正文也能完整收藏”的贴图式信息量。插图只承担当前段落中最难用文字快速看懂的一个关系或判断；标题、说明、四项清单和行动建议全部塞进一张图，造成图片替代正文、阅读时间过长或与贴图同构时，视为形式选择错误，必须减量或改回正文。

### 6. 自动验证

把事实卡和成品信息写入 JSON，运行：

```bash
python3 scripts/verify_edit_scope.py snapshot path/to/project --output /tmp/edit-baseline.json
python3 scripts/validate_package.py package.json
python3 scripts/check_image_density.py path/to/remotion-image-1.png path/to/remotion-image-2.png
python3 scripts/check_article_image_scale.py path/to/header.png path/to/remotion-image.png path/to/footer.png
python3 scripts/verify_edit_scope.py verify path/to/project --baseline /tmp/edit-baseline.json --allow src/TargetIllustration.tsx --lock public/ehafo-article-header.png=23081faf27778eb9372fccfe4ae82e7a7b48f748a0e5a3327e2c5de02b4a64c9 --lock public/ehafo-article-footer.png=e7ba40c3e1742c10958a91a764a8ab42a9eaab2352cd1f87cb260399cd4ec84d
```

`snapshot` 必须在任何文件修改前运行，`verify` 必须在渲染和交付前运行。`--allow` 使用相对项目根目录的精确文件路径，可重复传入；`--lock` 使用 `相对路径=预期SHA-256`，列出项目内所有固定资产，同时证明资产前后未变且仍是认可的原文件。验证包中每条门禁记录的 `scope_verified` 和 `locked_assets_verified` 只有在 `verify` 返回 `ok: true` 后才可写为 `true`。

只对新生成的 Remotion 文章正文信息图运行 `check_image_density.py`；文章封面、服务号贴图及固定品牌首尾图不得使用该脚本判定合格。封面按双比例和缩略尺寸验收，贴图按实际发布尺寸完成单张价值、整套一致性和手机端可读性验收。任一验证失败时修正后重跑；无法修正则返回 `BLOCKED`。验证脚本通过只说明对应确定性门禁合格，不证明事实天然正确、视觉天然优秀或用户价值成立；执行者仍必须完成官方来源语义核验、对应发布场景的手机端目视检查和独立用户测试。

`check_article_image_scale.py` 用于文章固定顶部图、全部正文信息图和固定底部图，检查典型有效行的横向内容跨度，防止大画布中的小内容被微信再次整体缩小。脚本失败时不得靠 CSS 放大、提高导出分辨率或让用户点击查看原图绕过；先裁掉无信息作用的画布，或重新排版使主要内容接近正文满宽。该脚本不用于服务号独立贴图。

文章正文插图的自动检查还必须包含一次外框目视门禁：分别查看图片素材本身和插入后的约 390px 页面，任一层出现包围整张图片的明显边框、圆角外壳、投影或异色背景，均不得交付；先删除外部框架并重新渲染、预览和验收。内部信息分区卡片不因此删除。

文章正文插图还必须包含一次“数量与解释价值门禁”：在 `outputs.article.illustrations` 中登记 1—2 张正文插图的路径和 `unique_information`，并由 `validate_package.py` 检查。0 张、超过 2 张、重复路径、把固定顶部图或底部图计入正文插图、缺少独有信息，均不得交付。若初稿没有适合可视化的关系，必须重新组织内容，从核心判断路径、步骤、对照或操作确认中选择 1 个最需要解释的模块制作插图；不得添加无信息作用的装饰图凑数。

文章正文插图还必须包含一次“长度与形式门禁”：按约 390px 正文宽度记录每张图的实际显示高度、纵向同构模块数量和所占连续屏幕长度。默认显示高度大于显示宽度、纵向堆叠超过 3 个同构卡片，或必须缩小普通文字才能塞进单图时，均不得交付；必须改成更紧凑的横向/分栏结构、拆图或将次要信息放回正文。不得因为脚本密度检查通过，就把贴图式竖长卡片当成合格文章插图。

文章正文插图还必须包含一次“内嵌完整性门禁”：在约 390px 的文章正文中以正常阅读状态查看，不点击放大，确认图片四边、标题和关键信息全部可见，且不存在横向滚动。发现左右缺失时，先检查是否从第三方排版工具复制了固定宽度模块，再检查图片或外层容器是否存在固定像素宽度、负边距、位移、溢出隐藏或裁切填充；修复后重新导入并验收。此门禁不用于服务号独立贴图。

修改既有文章中的顶部图、底部图或正文插图时，先单独修改并展示目标图片，不得同时改动 HTML。用户确认图片素材后，再插入原文章并检查整体效果；除非用户明确授权一次完成，不得跳过素材确认阶段。

文章 HTML 交付前必须完成两层预览：

1. 以约 390px 宽度检查中文、图片、滚动、间距、外框和横向溢出；
   - 正文插图必须在不点击放大的状态下完整显示；点击后才完整视为失败；
   - 图片保持原始宽高比并自适应正文宽度，图片与容器不得裁切或隐藏左右内容；
   - 文章 HTML 不得生成页面内复制控件、顶部预览工具栏或 Clipboard 脚本；检查对象必须是实际导入微信草稿箱并保存后重新打开的结果，不得只截图原始 HTML；逐张确认顶部图、正文信息图和底部图的主体宽度与文字可读性；
2. 提供可直接打开的在线网页预览；普通文件链接或静态长截图不得冒充在线预览。在线预览不可用时，明确说明原因，并同时提供 HTML 文件和实际手机端预览图。

首次使用或更换文章首图、正文信息图模板、尾图、图片内嵌方式或导入逻辑时，本地检查通过后仍只可标记为 `DRAFT_PASS`，直到用户把完整正文导入微信草稿箱、保存后重新打开并发送手机预览，确认图片未丢失、未变小、未裁切且文字可读。一次微信实测通过后，可以复用同一组未变更的资产和导入模板；任一相关资产、尺寸、样式或导入逻辑变化后必须重新实测。

微信编辑器规则变化、复杂模板复制失败或现有样式无法稳定保留时，不得把“更新 Skill”当作备用发布方式，也不得因此停止交付。立即读取 [article-mobile-layout.md](references/article-mobile-layout.md) 的“微信模板失效时的降级发布”，保留已核验正文和锁定品牌资产，移除不稳定的复杂样式，降级为微信原生基础排版并重新完成草稿箱与手机端验收。只有降级方案实测通过后，才把新兼容规则写回 Skill。

更新已有在线预览时复用原站点，不新建重复站点；发布后重新打开线上地址核对实际版本，不得只以本地构建成功作为交付依据。

### 7. 发布后复盘与规则回写

用户要求复盘已发布内容，或当前运行能够读取真实发布数据时，读取 [post-publication-loop.md](references/post-publication-loop.md)。

1. 先按内容任务选择指标和观察窗口，不用单一即时阅读量评价考讯、长期搜索内容、品牌内容和产品承接内容；
2. 区分即时表现、中期深度行为和长期搜索/转化，判断当前数据是否已经覆盖预先声明的观察窗口；
3. 每次复盘只保留最有证据的一至两项原因、一条可复用结论和一个需要更新的系统位置；
4. 事实错误回写事实卡或知识库，重复返工回写模板或门禁，用户高频问题回写选题库，稳定表现规律回写形式或生产规则；
5. 单篇、短窗口或异常样本只能形成待验证假设，不得直接升级为全局规则；
6. 没有真实数据访问权限时不编造结果，保持 `VALUE_UNPROVEN`，并按内容类型给出简短的后续观察计划。

### 8. 输出

按实际状态输出，不得把 `VALUE_UNPROVEN` 写成“可直接发布”。

`VALUE_UNPROVEN` 或 `AUTO_RELEASE` 时按顺序输出：

1. 状态；
2. 选题与用户价值；
3. 形式判断：选择了什么、排除了什么、简要原因；
4. 可直接发布的已选成品；
5. 图片生成提示词或图片成品（仅在选择贴图且用户需要时）；
6. 信息来源、官方链接和核验日期。

`VALUE_UNPROVEN` 必须明确说明“事实与用户任务测试已通过，但尚无真实发布数据证明效果”。`AUTO_RELEASE` 必须列出使用的同类历史内容、指标、基准和观察窗口。不要输出内部推理或冗长检查过程。

用户要求查看、审阅或确认文章成果时，必须在聊天中直接展示标题、摘要和完整正文；文件或预览链接只能作为补充，不得用修改摘要、检查结论或文件链接代替成稿。

交付文章 HTML 时，同时提供可打开的 HTML 文件、约 390px 手机端实际预览图和已验收的在线预览网址；不得声称普通 HTML 链接必然带有播放、全屏或预览卡片按钮。

`DRAFT_PASS` 时只输出：

1. 状态；
2. 已通过的事实与格式项；
3. 独立用户测试发现的未解决问题；
4. 下一轮必须修改的内容。

`BLOCKED` 时只输出：

1. 状态；
2. 阻断的具体事实；
3. 缺少或冲突的官方来源；
4. 系统下一次可重新运行的条件。

不得输出带有猜测日期或政策的正式稿。
